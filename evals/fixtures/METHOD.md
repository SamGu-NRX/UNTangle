# METHOD — measuring the campus-routes fixture

**Version 1.0.0 — 2026-10-11**
Applies to `evals/fixtures/campus-routes.json` (generated by
`evals/fixtures/tools/build-campus-routes.py`, which is the executable form of this document).

## Data-origin statement (read this first)

**Every number in `campus-routes.json` is map-derived.** Walking-path lengths are measured
from OpenStreetMap way geometry fetched over the public Overpass API. **No entry was
physically walked.** This is stated in the fixture itself
(`provenance.dataOrigin = "map-derived"`, `provenance.physicallyWalked = false`, and per-pair
`dataOrigin` / `physicallyWalked` fields). The numbers are estimates of real-world walking
distance with the accuracy of the OSM pedestrian layer in the area; they are a shared
reference for evals, not survey data.

## Inputs

| Input | Where | Used for |
|---|---|---|
| Building roster and pins | `frontend/src/lib/campus-locations.ts` at this branch | building ids, names, pin coordinates, `isOffCampus` |
| compD building set | `backend/data/compD.csv` (backend submodule pinned at `0a49d4d`) | the `inCompD` flag per building |
| Pedestrian ways | Overpass API, query below | the routing graph |
| Building footprints | Overpass API, query below | entrance coordinates |

The bbox used for both queries is the app's campus bounds (`north 33.216, south 33.204,
east -97.139, west -97.156`) widened by a ~0.0015° margin so perimeter-street crossings are
included: **`(33.2025, -97.1585, 33.2175, -97.1345)`** (south, west, north, east).

## Step 1 — Overpass queries

Two queries against `https://overpass-api.de/api/interpreter` (fallback:
`https://overpass.kumi.systems/api/interpreter`), retried up to 4 times alternating
endpoints with 15 s backoff; the raw JSON responses are kept as evidence
(`evidence/overpass-pedestrian-<STAMP>.json`, `evidence/overpass-buildings-<STAMP>.json`).

```
[out:json][timeout:180];
( way["highway"](33.2025,-97.1585,33.2175,-97.1345); ); out geom;

[out:json][timeout:120];
( way["building"](33.2025,-97.1585,33.2175,-97.1345); ); out geom;
```

`out geom` inlines each way's node coordinates, so no separate node download is needed.
The 2026-10-11 fetch returned ~1.66 MB of highway ways and ~1.13 MB of building ways.

## Step 2 — pedestrian graph

1. **Way filter.** Keep a way iff its `highway` tag is in
   `{footway, steps, path, pedestrian, corridor, living_street, service, residential,
   unclassified, tertiary, secondary, primary, tertiary_link, secondary_link, primary_link,
   track, road}` **and** `foot != "no"` **and not** (`access ∈ {no, private}` with
   `foot ∉ {yes, designated, permissive}`). This keeps sidewalks, campus paths, stairs,
   crossings, parking lots and the perimeter streets a pedestrian may legally use.
2. **Nodes and edges.** Every way contributes its consecutive node pairs as undirected
   edges; edge weight = haversine distance between the node coordinates (earth radius
   6,371,000 m). Nodes are keyed by their exact coordinates (rounded to 8 decimal places
   for keying only). Ways that share a node are therefore connected at that node — no
   extra joining step.
3. **Edge metadata.** Each edge remembers the set of contributing way ids and their
   classification: `footway=crossing` → `crossing`, `footway=sidewalk` → `sidewalk`,
   otherwise the `highway` value (`steps`, `service`, `residential`, `tertiary`, …).
   Classifications drive each pair's `wayTypes`, `roadCrossings` (edges classified
   `crossing`) and `stepsSegments` (edges classified `steps`).

Result for 2026-10-11: 2,597 walkable ways → 8,206 nodes / 9,895 edges.

## Step 3 — entrances (endpoint coordinates)

For each in-bounds building, in this order:

1. **Snap node.** Among all graph nodes within **250 m** of the building's bundled pin,
   take the nearest (haversine). All 15 in-bounds buildings snapped at ≤ 49.7 m
   (max: Wooten Hall); none hit the 250 m cap. Recorded as `snapNode` per building.
2. **Footprint.** Find every closed `building=yes` way whose polygon contains the pin
   (ray-casting point-in-polygon on raw lon/lat); if several (courtyards), take the
   smallest by shoelace area. The building's **entrance coordinate** is the point on that
   polygon's boundary nearest to the snap node (exact segment projection in a local
   equirectangular frame). Recorded per building with
   `entranceSource = "osm-building-footprint-edge"` and the `osmFootprintWayId`.
3. **Fallback.** If no OSM building polygon contains the pin (4 of 15 buildings: art,
   arta, gate, musi — footprints missing or mapped as relations), the entrance coordinate
   falls back to the bundled pin itself, with
   `entranceSource = "pin-fallback (no OSM building polygon contains the pin)"`.
4. `snapToNetworkMeters` = haversine distance from the entrance coordinate to its snap
   node (the straight "door to network" connector).

`ntdp` (Discovery Park) is outside the app's routing bounds, so it gets no entrance and no
pairs; it is listed for resolve-coverage in the suite.

## Step 4 — route measurement

- **Shortest path:** Dijkstra over the pedestrian graph between the two buildings' snap
  nodes. Route length = sum of haversine edge weights along the shortest path.
- **Walking length** recorded per pair =
  `snapToNetworkMeters(start) + networkRoute + snapToNetworkMeters(end)` — the two straight
  door-to-network connectors are part of the walk and are included (and separately
  recorded as `connectorMeters` and `networkRouteMeters`).
- **Great-circle baseline** per pair = haversine distance between the two entrance
  coordinates, recorded as `greatCircleMeters`. The recorded walking length is always ≥
  this baseline (triangle inequality); `verify-campus-routes.ts` re-asserts it from the
  recorded geometry alone.
- **Geometry** recorded per pair = entrance → snap node → graph path nodes → snap node →
  entrance, i.e. exactly the polyline the distance is computed from.

## Step 5 — rounding

- Coordinates (entrances, snap nodes, geometry vertices): **7 decimal places** (~1 cm).
- All distances (`distanceMeters`, `greatCircleMeters`, `networkRouteMeters`,
  `connectorMeters`, `snapToNetworkMeters`): **1 decimal place**.
- The self-check tolerance is therefore 0.5 m between a re-derived polyline length and the
  recorded `distanceMeters`, and 0.05 m on the great-circle inequality.

## Step 6 — pair selection (deterministic)

From the 105 in-bounds building pairs (15 choose 2, all routable):

1. up to 3 pairs whose route uses steps (sorted by pair id);
2. up to 4 additional pairs ranked by most road-crossing edges (ties by pair id);
3. greedy coverage fill: pairs that add the most not-yet-covered buildings first (ties by
   shorter route, then pair id), until 18 pairs and every in-bounds building is an
   endpoint;
4. if still short, the longest remaining routes are added.

This yields 18 pairs spanning the campus, 11 of which include road crossings and 10 of
which include steps (see `wayTypes` / `roadCrossings` / `stepsSegments` per pair). Path
lengths run 1.23×–1.97× their great-circle baseline.

## Step 7 — visual check (evidence)

Every pair's route is drawn over the rendered openstreetmap.org raster tiles and
screenshotted:

- `tools/render-evidence.py` renders one Leaflet page per pair (plus an overview of all
  pairs) with the recorded geometry as a polyline, start marker (green) and end marker
  (red), and screenshots it with Playwright chromium:
  `PLAYWRIGHT_BROWSERS_PATH=/home/user/work/pw-browsers bun x playwright install chromium`,
  then `bun x playwright screenshot --viewport-size=1280,900 --wait-for-timeout=9000
  file://...#<pairId> out.png`.
- Output: `evidence/route-<pairId>.png` (one per pair) and `evidence/overview-pairs.png`.
  Each per-pair image is named in that pair's `evidence` field.
- A human or agent reviews the PNGs: the polyline must follow walkable paths (no routing
  across building interiors or restricted roads) and start/end at the stated buildings.

## Reproducing every number from scratch

```bash
git clone https://github.com/SamGu-NRX/UNTangle.git && cd UNTangle
git checkout <this branch>
git submodule update --init backend          # read-only, pins compD.csv at 0a49d4d
python3 evals/fixtures/tools/build-campus-routes.py --refresh-osm   # refetch OSM
PLAYWRIGHT_BROWSERS_PATH=/home/user/work/pw-browsers bun x playwright install chromium
python3 evals/fixtures/tools/render-evidence.py
bun evals/fixtures/verify-campus-routes.ts   # exit 0 = fixture internally consistent
```

Numbers may shift a few meters when OSM contributors edit the campus — that is expected;
the raw Overpass responses stored in `evidence/` pin down the exact data used for this
fixture version.
